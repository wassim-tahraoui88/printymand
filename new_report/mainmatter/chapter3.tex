\section{Requirements specification}
\subsection{Identification of actors}
An actor represents any external entity that interacts with the system.
In Printymand, we identified five main actors:

\begin{itemize}
    \item \textbf{Visitor:} explores the public pages of the platform and can create an account or log in.
    \item \textbf{Customer:} browses the marketplace, customizes products, selects printers, manages the cart, places orders, tracks fulfillment, and submits reviews.
    \item \textbf{Designer:} publishes artworks, manages design information, configures product compatibility, and follows sales and engagement indicators.
    \item \textbf{Printer:} manages printable products, receives order lines, and updates production statuses.
    \item \textbf{Administrator:} supervises users, roles, ranks, content, platform indicators, and system health.
\end{itemize}

\subsection{Functional requirements}
Functional requirements describe the actions that the system must perform. The main functional requirements of Printymand are:

\begin{itemize}
    \item The system must allow users to register and authenticate according to their role.
    \item The system must protect private pages and API resources through authentication and role-based authorization.
    \item The system must display a home page, marketplace page, product catalog, and design detail page.
    \item The system must allow customers to customize a selected design on an available product by changing color, size, position, and scale.
    \item The system must allow customers to select a printer before adding a customized product to the cart.
    \item The system must allow cart review, checkout, payment method selection, and order confirmation.
    \item The system must provide order tracking through a timeline based on production and delivery status.
    \item The system must allow customers to manage profile information, saved addresses, payment preferences, and reviews.
    \item The system must allow designers to manage designs, product assignments, profile information, and analytics.
    \item The system must allow printers to manage printable products and update fulfillment statuses.
    \item The system must allow administrators to supervise users, content, roles, ranks, and platform activity.
    \item The system must provide health and monitoring information for administration.
\end{itemize}

\subsection{Non-functional requirements}
Non-functional requirements define the quality attributes of the system:

\begin{itemize}
    \item \textbf{Security:} authentication is based on JWT, passwords are hashed, and access is controlled through role-based authorization.
    \item \textbf{Usability:} the interface is organized around clear navigation, reusable components, forms, dashboards, and visual feedback.
    \item \textbf{Maintainability:} the system uses a modular architecture separating interface, services, application logic, domain contracts, and infrastructure.
    \item \textbf{Reliability:} validation, exception handling, logging, and transactions contribute to stable behavior.
    \item \textbf{Scalability:} the database model separates users, designs, products, printers, orders, and related entities, which supports marketplace growth.
    \item \textbf{Performance:} pagination, local state management, and request throttling help maintain a responsive user experience.
\end{itemize}

\section{System architecture}
Printymand follows a client-server architecture.
The client side is a single-page Angular application responsible for interaction, navigation, state management, and user interface rendering. The server side is a NestJS REST API responsible for authentication, authorization, business operations, validation, persistence, and monitoring. PostgreSQL is used as the relational database.

\reportfigure{system-architecture}{figures/system-architecture-diagram.png}{System architecture diagram.}

\subsection{Front-end architecture}
The front-end application was implemented with Angular and TypeScript.
We adopted a component-based architecture to make the interface reusable and maintainable.
Pages represent complete views such as home, marketplace, products, design details, customization, printer selection, checkout, tracking, and dashboards.
Components such as design cards, product cards, printer cards, stat cards, rank badges, modals, dashboard shells, and image fallback elements are reused across several pages.

Services centralize application logic.
The authentication service manages user access, role redirection, logout, and profile updates.
The workflow service coordinates designs, products, printers, cart items, orders, reviews, payouts, and dashboard indicators.
The API service communicates with the REST back end.
This separation makes the front end easier to maintain and allows each page to focus on presentation and user interaction.

\subsection{Back-end architecture}
The back-end application was implemented with NestJS and TypeScript.
We adopted a layered architecture composed of:

\begin{itemize}
    \item \textbf{API layer:} controllers, guards, decorators, filters, interceptors, and request DTOs.
    \item \textbf{Application layer:} use cases that implement business operations such as login, registration, product creation, design publication, dashboard retrieval, and session management.
    \item \textbf{Domain layer:} entities, DTOs, repository contracts, policies, and value objects.
    \item \textbf{Infrastructure layer:} JWT services, PostgreSQL persistence, transactions, health checks, and realtime services.
\end{itemize}

This architecture separates business logic from technical details and improves testability, readability, and extensibility.

\subsection{Authentication and authorization}
Authentication is handled through JWT tokens.
During registration or login, the server verifies the user information, signs a token, and sends it to the client through an HTTP-only cookie.
Passwords are hashed with bcrypt.
The platform also supports token extraction from authorization headers for API usage.

Authorization is based on RBAC. Guards verify that a user is authenticated and has the required role before accessing protected resources.
The same principle is applied in the Angular application through route guards that redirect users to the correct dashboard according to their role.

\subsection{Main API modules}
The REST API is organized into modules that reflect the platform domains:

\begin{itemize}
    \item \textbf{Authentication:} registration, login, logout, refresh, and current user retrieval.
    \item \textbf{Products:} product creation, listing, and details.
    \item \textbf{Designs:} design publication, listing, upload configuration, and details.
    \item \textbf{Dashboard:} global and role-related indicators.
    \item \textbf{Cart and orders:} cart workflow, order confirmation, and tracking operations.
    \item \textbf{Health:} administrator monitoring of memory and database connectivity.
\end{itemize}

\section{Work environment}
\subsection{Software architectural pattern}
For the front end, we used a component-service architecture.
Components define interface elements and views, while services centralize authentication, workflow, and API communication.
For the back end, we used a layered architecture inspired by clean architecture principles, separating controllers, use cases, domain contracts, and infrastructure.

\subsection{Modeling language}
We used UML to model the system because it provides a clear and standardized way to represent actors, use cases, classes, and interactions.
UML diagrams helped us understand the system before implementation and communicate design decisions more effectively.
